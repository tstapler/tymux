# Pre-mortem: unix-socket-auth
**Date**: 2026-08-29

## Failure Modes

| # | Failure | First Symptom | Prevention | Severity |
|---|---------|--------------|------------|----------|
| 1 | "Both-by-default" TCP loopback plus `tymux-cli`'s `dial_channel` blanket `Err(_) =>` fallback (Task 6.2.1b, `crates/tymux-cli/src/main.rs`) means any UDS rejection — including the OS-level `EACCES` a mismatched-uid client gets on a `0600` socket, before `peer_is_authorized` ever runs — is treated identically to "no daemon there," and the client silently redials over the fully unauthenticated TCP loopback and succeeds. The peer-cred gate protects only clients that don't try the fallback path. | A security review or pentest: a non-owning local user runs `tymux ls` (or any client using default dialing) against another user's `tymuxd`; it exits 0 and lists/attaches sessions, with only a one-line stderr notice ("falling back to TCP loopback") that a script or CI log silently swallows. The exact scenario `requirements.md`'s Problem Statement says this project exists to close. | Change `dial_channel` to distinguish "no listener" (`ConnectionRefused`/`NotFound` → fall back with warning, current behavior) from "listener present but access denied" (`EACCES`/`PermissionDenied` → hard error, never fall back to TCP). Add an AC/integration test asserting a peer-cred-rejected client does *not* succeed via automatic TCP fallback. Until `--disable-tcp-loopback` is the recommended/default posture, stop describing this feature's shipped default state as delivering the isolation guarantee — the guarantee only holds once TCP is disabled. | P1 |
| 2 | `bind_uds_listener` (Task 2.2.1a) only `create_dir_all`s + `chmod(0700)`s the parent directory "when it does not already exist" and explicitly "trusts its current permissions" otherwise. On the `$TMPDIR`/`/tmp` fallback branch (any host where `$XDG_RUNTIME_DIR` is unset — non-systemd-session shells, cron, some containers, and the documented macOS path when `$TMPDIR` itself isn't uid-scoped), an attacker on the same host can pre-create `/tmp/tymuxd-<uid>/` with permissive/malicious permissions *before* the legitimate daemon's first start; `create_dir_all` succeeds against the pre-existing directory without checking its owner or mode, so the attacker keeps write access to the directory the socket lives in. | An operator or security reviewer notices `/tmp/tymuxd-<uid>/` is group- or world-writable after a clean start on a host where `XDG_RUNTIME_DIR` is unset, or a stale/attacker-controlled socket file is found there that predates the daemon's own start time. | Make `bind_uds_listener` validate (not trust) a pre-existing parent directory: fatal error unless it's owned by the daemon's own uid and mode is `0700` (or `0750`/`0770` matching the group-access case) — never silently proceed. Add the AC/test this plan's own six ACs are missing: "a world-writable pre-existing parent directory owned by a different uid causes `bind_uds_listener` to fail loudly, not bind into it." | P1 |
| 3 | The one integration test that would prove the feature's actual security property — a real client with a genuinely different OS uid being rejected via kernel-delivered `peer_cred()` — ships `#[ignore]`/skipped in all three clients on this repo's actual CI (Tasks 6.4.1c/7.3.1b/8.3.1c, per the plan's own resolved Unresolved Question), on every platform including macOS. Only a synthetic in-process `UCred` (unit test) and same-uid accept paths are ever exercised in CI. | A regression in `peer_is_authorized`, `PreAuthorizedUnixStream`, or the umask/bind sequence that breaks real cross-uid rejection ships and passes CI green, because CI structurally cannot exercise the one path that matters. | Before calling this project done, stand up the one root-capable (or `unshare --user`, per pitfalls.md §7) CI job needed to run the real cross-uid reject test at least once per merge to `main`/release branch, or explicitly ticket it with a date and owner in `validation.md` rather than leaving "Owner: N/A unless requested" — an unowned gap on a solo-maintainer repo does not get picked up on its own. | P2 |
| 4 | `--socket-group` grants full daemon control (not scoped access) — documented in Deployment Guidance and flag help text — but under access-friction pressure ("my teammate can't connect"), the path of least resistance for a solo/small-team operator is exactly the Docker-`docker`-group move this project explicitly avoided structurally, just reintroduced socially. Compounding this: the same `--socket-group` config behaves differently across platforms (Linux checks full supplementary-group list via `/proc`; macOS/BSD check only primary gid — ADR-002), so an identical config file/flag deployed on a mixed Linux/macOS fleet silently grants different access on each host. | A support/incident report: "I added myself to the configured group but still can't connect" (macOS, secondary-group case) or "I didn't realize that group grants full session control, not read-only" (any platform) — discovered only after broader access was already granted. | Log the full-access + platform-inconsistency caveat once at every `tymuxd` startup when `--socket-group` is set (not only in static `--help` text an operator may never read), and add a doc/matrix test making the Linux-vs-macOS behavioral gap explicit and testable, not just narratively documented. | P2 |
| 5 | This is a solo-maintainer repo with "no external deadline" (requirements.md Constraints) carrying two listener code paths indefinitely; the TCP-removal follow-up project has no ticket, date, or owner (Risk Control, Unresolved Questions) — only a repeated startup `tracing::warn!`. Log-fatigue makes a warning that fires identically on every start invisible within weeks, and nothing forces the removal project to actually get scheduled. | Six-plus months post-ship: `git log`/issue tracker shows no follow-up TCP-removal work has started; the startup warning is still firing unchanged; TCP loopback is still open and unauthenticated by default on every install. | Before shipping, file a dated tracking issue for the TCP-removal project (even without committing to a hard deadline) and reference its number from the deprecation warning text/`plan.md`, so "temporary" has a forcing function beyond memory. Consider escalating the warning's framing over time (e.g., naming a target version) rather than a static message. | P2 |

## P1 Items (address before implementation)
- [x] #1 — Fixed 2026-08-29: Story 6.2.1 (and Go/TS equivalents, Epics 7.2/8.2) now
  require `dial_channel`/`dial_uds` to classify errors — `ConnectionRefused`/`NotFound`
  falls back to TCP with the existing notice; `PermissionDenied`/`EACCES` returns a hard
  error, never falls back. New non-CI-skipped integration tests (Tasks 6.4.1d, 7.3.1c,
  8.3.1d) prove a peer-cred-rejected client never ends up connected via TCP fallback.
- [x] #2 — Fixed 2026-08-29: Story 2.2.1 (`bind_uds_listener`) now validates (not
  trusts) a pre-existing parent directory via `symlink_metadata` uid/mode checks,
  fatal-erroring on wrong ownership or overly-permissive mode instead of binding into
  it as-is. Task 2.2.1b adds the corresponding tests (10 tests for 10 ACs).
