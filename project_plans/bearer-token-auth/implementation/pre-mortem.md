# Pre-mortem: bearer-token-auth
**Date**: 2026-08-28

## Failure Modes

| # | Failure | First Symptom | Prevention | Severity |
|---|---------|--------------|------------|----------|
| 1 | The auth gate keys off `tymuxd`'s own bind address (`socket_addr.ip().is_loopback()`), not actual network reachability. An operator who fronts a loopback-bound `tymuxd` with an nginx/Caddy reverse proxy, an SSH `-L` tunnel, or a Cloudflare/ngrok tunnel — a completely standard way to add TLS or remote access to a plaintext-only gRPC daemon — gets a daemon that thinks it's "loopback, no auth needed" while it is, in fact, reachable from the internet with zero token check. | Unexplained sessions/panes running commands nobody on the team ran (crypto-miner, reverse shell, data exfiltration via `CapturePane`), discovered by resource abuse or a `ListSessions` audit — not a crash, not a log line, since the daemon never logged a rejection (nothing was ever rejected). | Add an explicit deployment-doc/plan note: any tymuxd fronted by a proxy or tunnel MUST bind non-loopback + set a token, full stop, regardless of what the proxy's own auth does — the bind-address heuristic is a proxy for reachability, not a guarantee of it. Consider also logging a one-time startup hint when loopback-bound: "if this daemon is reachable through a reverse proxy or tunnel, loopback auto-exemption does not protect you." | P1 |
| 2 | Epic 1.3 stops the token leaking into *spawned panes'* environment, but nothing addresses the much larger set of ordinary ops surfaces that expose a raw env var/CLI flag in a real deployment: `systemctl show`/`journalctl` on a systemd unit, `docker inspect`/`docker history` on a container, `/proc/<pid>/environ` (readable by any UID in the same PID/user namespace on some container configs), shell history from typing `--token` inline, or a CI/deploy pipeline that echoes its env before exec'ing the daemon. | A security-conscious operator or auditor finds the live token in `docker inspect` or systemd unit status during a routine review, or a CI log leak is discovered after the fact. | Prioritize the already-identified `TYMUXD_TOKEN_FILE` fast-follow (currently deferred with no owner) ahead of, or immediately after, this project's ship, and add an explicit deployment-doc warning against putting `TYMUXD_TOKEN=` directly in unit files/compose files/CI env blocks. | P2 |
| 3 | The plan's own Unresolved Questions confirm there is no live-reload: rotating a leaked token requires a full daemon restart, which — per the same section — has no mechanism to gracefully close in-flight `Attach` streams, so it forcibly drops every attached session network-wide. This creates a bad operational incentive: the fastest fix for a suspected leak (rotate + restart) is also the most disruptive action available, which in practice means operators delay rotating a compromised token exactly when they should act fastest. | An operator notices suspicious `ListSessions`/`CapturePane` activity, hesitates to restart because it will kill N live agent sessions mid-task, and the exposure window stays open longer than it should. | Document this trade-off explicitly in a runbook (not just an Unresolved Question with "Owner: N/A"), and treat `TYMUXD_TOKEN_FILE` + a SIGHUP-style config-reload path as a higher-priority fast-follow than currently scoped — reload-without-restart is the actual fix for the incentive problem, not just file-based distribution. | P2 |
| 4 | The bearer token is one shared, unscoped secret that grants full RPC access forever. The roadmap's very next items — per-session/pane ownership and scoped tokens — are described as "layered on top of" this token, not replacing it. Nothing in this plan requires the future scoped-token design to constrain or deprecate the original master token's blast radius. If scoped tokens ship as purely additive, a leaked *scoped* "read-only" token is no safer than today, because the original master token (or a scoped-token implementation bug that falls back to master-token semantics) still bypasses ownership checks entirely. | Months from now: a scoped read-only token leaks, and an incident review discovers it (or the original master token) still permits `KillSession`/`CreateSession`, because the interceptor's original all-or-nothing check was never narrowed when scoped tokens landed. | Add an Unresolved Question / forward-looking plan note now (cheap to write today, easy to forget later) stating that the scoped-token design must explicitly define the master token's post-scoping role — e.g., restrict it to bootstrap/admin use, or require it be retired — rather than leaving "layered on top" ambiguous. | P2 |
| 5 | The plan explicitly frames Epic 1.3 (the PTY env-leak fix in `crates/tymux-core/src/pane.rs`) as independent and parallelizable with no dependency on the main auth epics — true for scheduling, but it also means a subagent-driven implementation run organized around the "auth interceptor" epics can deprioritize or silently drop it, since it's the one epic that touches a third crate, isn't gated by anything, and isn't part of the reviewed core interceptor logic both existing reviews focused on. Neither adversarial-review.md nor architecture-review.md re-verified Epic 1.3 at all in their re-checks. | `env`/`printenv` run inside any pane on a shared, non-loopback `tymuxd` reveals `TYMUXD_TOKEN` to every authenticated multi-tenant user — discovered by a user (or a malicious session), not by CI, since the failure mode is the task being skipped entirely, not written incorrectly (its own regression test would only fail if the code were written and wrong, not written and missing). | Add Epic 1.3 as a named, explicit item in validation.md's ship checklist (grep for `env_remove("TYMUXD_TOKEN")` in `pane.rs` + confirm its regression test passes) rather than relying on the epic-dependency graph to organically ensure it lands — this is exactly the class of "forgotten independent task" a completion checklist exists to catch. | P1 |
