# Pre-mortem: attach-resume-protocol
**Date**: 2026-08-24

## Failure Modes

| # | Failure | First Symptom | Prevention | Severity |
|---|---------|--------------|------------|----------|
| 1 | The `AttachEvent.output` wire change (`bytes` → `OutputChunk` message, "same field number") is not actually wire-compatible for old clients — `bytes` and embedded `message` share protobuf wire type 2, so a still-deployed `clients/go@v0.1.0` consumer (stapler-squad's `BackendTymux`, explicitly required by the Constraints section to keep working unmodified) will successfully *parse* field 1 but interpret the new submessage's raw framing (varint seq tag + length-prefixed data) as if it were raw pty bytes. Epic 2.4's test only checks the server's construction logic when `resume_from_seq` is absent — it never exercises an actual old-generation client stub against the new wire format. | Immediately after any `tymuxd` upgrade to this branch, stapler-squad's still-pinned v0.1.0 client starts rendering garbled/binary-looking output (or hits a Go unmarshal error) on every attached pane, even though it never sent a resume token and did nothing differently — a silent production break with no code change on the consumer side. | Either (a) add a real compat test that runs an actual `clients/go@v0.1.0`-generated stub against a `tymuxd` built from this branch and asserts on the resulting (broken) output, converting the assumption into a falsifiable check before it ships; or (b) avoid the break at the wire level — add `OutputChunk` at a new field number (e.g. field 7) while leaving the legacy `bytes output = 1` populated for one release, then retire it in a later breaking bump, matching how field-preserving breaking changes are normally staged. | P1 |
| 2 | ADR-004's backoff schedule (200ms, x2, capped 8s, 8 attempts) sums to ~28.6s of retry time before the client gives up — well under ADR-003's 60s `grace_period_duration`. A daemon restart/upgrade that legitimately takes 30-60s (a real scenario the grace period was explicitly built to survive, per requirements.md's own "deliberate restart during an upgrade" example) causes every attached `tymux-cli` client to exit with a give-up error *before* the server-side safety net it's supposed to rely on has even expired. | During any daemon restart in the 30-60s range, users see `tymux attach` sessions exit with an error message instead of silently resuming, despite the pane still being alive and resumable server-side for the full grace window. | Cross-check the two defaults explicitly: either extend the backoff ceiling/attempt count so the schedule's total duration is >= `grace_period_duration`, or document the gap as an accepted tradeoff. Add a unit test asserting `sum(backoff_schedule) >= grace_period_duration` so a future change to either constant can't silently reopen the gap. | P2 |
| 3 | `heartbeat_timeout` (45s, "client-side threshold: no event received within this long marks the connection suspect and triggers reconnect") is defined in the Domain Glossary but no task in Phase 3 or Phase 6 actually implements it. Epic 6.1's reconnect loop (Task 6.1.1a) only reacts to `maybe_event?` returning an error or an unattributed `None` — i.e., to the stream actually terminating. A connection that goes silent without erroring (a NAT/proxy that keeps the TCP session looking alive with no traffic — exactly the scenario the requirements doc's Success Metrics section calls out) never triggers this path. | A client on a flaky NAT/proxy path stops receiving output and heartbeats but the stream never errors — the CLI hangs indefinitely with frozen output, no reconnect attempt, and no error message, reproducing the same block-forever bug class the disconnect-survival fix was built to close, in a new subsystem. | Add an explicit task implementing a client-side idle timer (`tokio::select!` racing `maybe_event?` against a 45s timeout reset on every received event, heartbeats included); on timeout, enter the same reconnect path as a stream-termination error. Add a test using a test double that goes silent without closing the stream, asserting the CLI still reconnects within `heartbeat_timeout` + backoff. | P2 |
| 4 | The replay buffer is budgeted by bytes (256KiB default), not by time, so a high-throughput pane (a build log, `docker logs -f`, anything verbose) evicts its entire retention window in a fraction of a second under sustained output — collapsing the "tolerate a real reconnect window" promise to near-zero for exactly the busiest, most disruptive-to-lose sessions. The `GapExceeded` counter/log carries `oldest_available_seq` but nothing about *why* the gap happened, so real usage data can never distinguish "buffer too small for this pane's throughput" from "client genuinely gone a long time" — the exact tuning signal the plan's own Feasibility Risks section says it needs. | `tymux_attach_resume_outcome_total{outcome="gap_exceeded_fallback"}` climbs specifically on busy panes even for brief (sub-second) disconnects, while quiet panes resume fine — but nothing in the current logs/metrics lets a maintainer see this correlation without manually cross-referencing pane output volume. | Add `oldest_retained_age_ms` (wall-clock age of the oldest surviving entry at the moment of eviction) to the `GapExceeded` warn-log and/or counter tags, so buffer-too-small can be told apart from client-genuinely-gone from the logs alone. Consider a hybrid budget (byte cap plus a minimum retained-duration target) rather than byte-only sizing. | P3 |
| 5 | `allocate_replay_budget()` is a hard cap evaluated once, at pane-spawn time, against whatever remains of the fixed 64MiB global budget — never rebalanced afterward. In a long-running daemon session with many panes opened over hours/days (a normal tmux-like usage pattern), panes spawned later can be granted 0 bytes permanently, even if earlier panes are mostly idle and could release headroom. Nothing surfaces a pane's granted budget anywhere observable. | A user with many long-lived panes finds that resume silently never works for panes opened later in the session (`resumed_from_buffer` stays at 0 for them) — discovered only by surprise the first time they actually need it, with no prior signal that those panes were ever running degraded. | Surface the granted `replay_budget_bytes` at spawn time (e.g. a `tracing::debug!` line, or an existing pane-info RPC field) so a `0`-byte grant isn't silent, and/or release/reclaim budget from long-idle panes so it can be redistributed instead of being permanently pinned by spawn order. | P3 |

## P1 Items (address before implementation)
- [x] #1 — Add a real old-client-stub compat test (or restage the wire change to a new field number with the legacy `bytes output = 1` kept populated for one release) before Epic 1.1/1.2 ship, so the plan's explicit "must not break stapler-squad's already-merged BackendTymux" constraint is actually verified rather than assumed from field-number preservation alone.
  - **Resolved via the restage option**: plan.md's Story 1.1.1/Task 1.1.1a/1.1.1b now add `OutputChunk output_chunk = 7;` as an additive sibling field, leaving `bytes output = 1;` completely untouched (dual-write in Task 2.2.1c); ADR-001 was revised accordingly. The belt-and-suspenders compat test was also added (Task 2.4.1c), so this was resolved by restructuring the plan, not merely by detecting the risk with a test alone.
