# Pre-mortem: stapler-squad-integration
**Date**: 2026-08-21

## Failure Modes

| # | Failure | First Symptom | Prevention | Severity |
|---|---------|--------------|------------|----------|
| 1 | The `setsid()` fix (ADR-002, Story 1.1.2) addresses a hypothesis confirmed on exactly one real-hardware repro pass; production hosts differ (containerized deploy, systemd already a session leader, a different PAM/init stack), and the real mechanism only partially overlaps with "tymuxd retains a controlling terminal" | Agent panes still die on abrupt disconnect in production even though `pane_survives_abrupt_disconnect` (Story 1.1.3) passes 10/10 in the dev-hardware CI environment | Story 1.1.2's acceptance criteria only requires "re-run the exact Task 1.1.1a repro." Add a second validation pass on a second, differently-configured environment (containerized + a systemd-managed host, not just the one machine used for discovery) before Epic 1.1 is marked done, and add a production log line (`setsid` outcome is already logged per the Observability Plan, but add a companion "pane exited within Nms of an Attach stream drop" signal) so a recurrence is detectable from logs alone, not just from a user complaint | P1 |
| 2 | Story 1.7.2's load test only exercises a concurrent `CreateSession` burst; the requirements' own Feasibility Risks section names the actual danger scenario — a mass **reconnect** of ~1,000 standing `Attach` streams (e.g. after a stapler-squad restart or a `tymuxd` upgrade) — and this path (per-pane broadcast resubscribe, `CapturePane` resync, `ReconnectLoop`'s backoff) was never load-tested at concurrency, only unit-tested for a single stream (Task 2.5.2d) | After a stapler-squad restart or deploy, the dashboard shows a wall of "reconnecting" sessions for tens of seconds to minutes, or `ReconnectLoop`'s backoff causes some sessions to give up and surface as permanently disconnected, even though `CreateSession` latency itself is fine | Add a concurrent-reconnect load test (extend Epic 1.7 with a Story 1.7.3, or fold into Story 2.5.2d) that drops N standing `Attach` streams simultaneously at n≈1000 sessions and measures reconnect latency / failure rate against a concrete threshold, the same way Story 1.7.2 measures `CreateSession` — before Epic 3 sign-off, not deferred to "find out in production" | P1 |
| 3 | Second-order interaction between two already-"resolved" pieces: Epic 1.1's `setsid()` fix is what lets a pane's process survive `tymuxd` dying or losing its controlling terminal, but Story 2.5.3 independently confirms `tymuxd` persists no OS PID and `revive_session` always spawns a **new** process on restart, never reattaching to the old one. No story reaps, signals, or even inventories those now-permanently-orphaned survivor processes | `ps` on the host shows an accumulating population of orphaned shell/agent processes with no owning `tymuxd` session after each daemon restart/deploy/crash; over weeks this becomes a slow, silent resource leak (CPU, memory, possibly still-running agent loops burning API credits) with no metric or alert surfacing it | Add a story that either (a) has `tymuxd` persist real OS PIDs and reap/`SIGTERM` orphaned children it can no longer reattach to at startup, or (b) explicitly documents this as an accepted trade-off and ships a `tymux_orphaned_process_count` metric plus a manual cleanup runbook, so the leak is at minimum visible rather than silent | P1 |
| 4 | The `go.mod replace` directive (Story 2.1.1) plus a CI sibling-checkout of tymux at `main` HEAD (Task 2.1.1b) couples stapler-squad's CI to tymux's unpinned tip indefinitely; the plan's own Unresolved Questions section leaves "tagged module vs. indefinite replace" open with no forcing deadline ("owner: whoever closes out Epic 3") | stapler-squad's CI goes red after a stapler-squad-unrelated commit merges to tymux's `main` (a proto field rename, a breaking Go client change), with no obvious correlation in the failing PR's own diff | Pin the CI sibling-checkout to a tagged SHA (not `main`), not an unbounded moving target, and give the tagged-vs-replace decision an explicit owner and date rather than leaving it open past "shipped." At minimum, add a scheduled or tymux-PR-triggered cross-repo compatibility check so a breaking tymux change is caught in the tymux PR, not discovered later in stapler-squad's CI | P2 |
| 5 | Requirements' primary success metric — "output fidelity indistinguishable from `BackendTmux`" — is verified only by one manual side-by-side pass with one agent (Claude Code, Story 3.1.1), with no automated regression test for `CellSGRRenderer`'s edge cases (256-color/truecolor, alt-screen, the `dim`/alt-screen gaps `ux.md` already flagged for `CapturePane`) or for other agent types (Codex, Gemini, Aider) with different TUI chrome | Weeks after ship, a user running a different agent type or hitting an edge-case terminal sequence sees garbled/missing styling through `BackendTymux` that the one manual Claude Code pass never exercised, and there's no automated test that would have caught it | Add an automated golden-output test as part of Epic 2.6/3.1: capture known ANSI/SGR sequences (bold, 256-color, truecolor, alt-screen) through both `BackendTmux` and `BackendTymux`'s `CellSGRRenderer` and diff byte-for-byte, instead of relying solely on one manual pass with one agent type as the parity gate | P2 |

- [x] #2 — Add a concurrent mass-reconnect load test (new Story 1.7.3 or an extension of Story 2.5.2d) exercising N standing `Attach` streams dropped and reconnected simultaneously at n≈1000, with a concrete pass/fail threshold, gating Epic 3 sign-off. *(Resolved in plan.md: Story 1.7.3 added with Tasks 1.7.3a-c and an explicit sign-off gate.)*
- [x] #3 — Add a story addressing orphaned-process accumulation after `tymuxd` restart: either real reap/signal-on-startup behavior, or at minimum an explicit documented trade-off plus an `tymux_orphaned_process_count` metric and cleanup runbook. *(Resolved in plan.md: Story 1.1.4 added, choosing the documented-trade-off + metric + runbook option with stated reasoning.)*
