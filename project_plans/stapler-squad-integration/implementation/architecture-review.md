## Prior Blockers — re-verified against the edited plan

- [x] **RESOLVED — Epic 2.1 / Story 2.1.3, per-session `BackendTymux` selection.** Original blocker: `NewProcessManager` checks the global `getSelectedBackend()` before `defaultBackend`, so passing `BackendTymux` as `defaultBackend` could never win. Verified live code unchanged since the original finding — [`session/backend_factory.go:32-39`](file:///home/tstapler/Programming/stapler-squad/session/backend_factory.go) still reads `backend := getSelectedBackend(); if backend == "" { backend = defaultBackend }`, and all four production call sites still pass `BackendTmux` as `defaultBackend` with an empty `ProcessManagerOptions{}` — confirmed by direct read at [`session/instance.go:768`](file:///home/tstapler/Programming/stapler-squad/session/instance.go#L768), [`session/instance_tmux.go:121`](file:///home/tstapler/Programming/stapler-squad/session/instance_tmux.go#L121), [`session/instance_serialization.go:324`](file:///home/tstapler/Programming/stapler-squad/session/instance_serialization.go#L324), [`session/external_discovery.go:165`](file:///home/tstapler/Programming/stapler-squad/session/external_discovery.go#L165) — all four literally read `NewProcessManager(context.Background(), BackendTmux, ProcessManagerOptions{})`, matching the plan's own citation exactly.
  The plan's fix (Story 2.1.3, revised text, plan.md:471-489; Task 2.1.3b, plan.md:483-485) adds a *new*, distinct `ProcessManagerOptions.Backend` field checked **ahead of** the global (`backend := opts.Backend; if backend == "" { backend = getSelectedBackend() }; if backend == "" { backend = defaultBackend }`), rather than trying to repurpose the already-dead `defaultBackend` param. This is a structurally different (correct) fix from the original story's premise, and it is internally consistent: `ProcessManagerOptions` today (`process_manager.go:78-85`, confirmed by direct read — no `Backend` field yet) has room for the new field with no collision; the global fallback path is untouched for any caller leaving `opts.Backend` unset, so existing behavior at all four call sites is preserved until Task 2.1.3c explicitly threads a per-session value through. Task 2.1.3d's unit test ("set global to `BackendTmux`, call once with `opts.Backend: BackendTymux`, assert `*BackendTymux`; call again with `opts.Backend` unset, assert the global `*TmuxBackend` is still returned") correctly matches the revised precedence and the real return type of the `BackendTmux` case (`newTmuxBackendFromOpts` returns `*TmuxBackend`, confirmed by read). The story would work as written if implemented.

- [x] **RESOLVED — Epic 1.2 / Story 1.2.3, `ExitStatus` wire-shape change breaking `tymux-cli` compilation.** Verified both cited construction sites still exist exactly as described: [`crates/tymux-cli/src/main.rs:554-559`](file:///home/tstapler/Programming/tymux/crates/tymux-cli/src/main.rs#L554-L559) (production, `Some(attach_event::Payload::Exited(_)) => { ... chrome_message_for_event(&attach_event::Payload::Exited(true)).unwrap() ... }`) and `main.rs:962` (test, `chrome_message_for_event(&attach_event::Payload::Exited(true))`) — both would fail to type-check once `bool exited` becomes `ExitStatus exited` (confirmed still `bool exited = 3;` today at [`proto/tymux/v1/tymux.proto:267`](file:///home/tstapler/Programming/tymux/proto/tymux/v1/tymux.proto#L267), inside the `oneof` at line 263-274, matching the plan's citation).
  New Task 1.2.3c (plan.md:244-246) fixes both sites: the production arm is rewritten to `Some(ref payload @ attach_event::Payload::Exited(_)) =>` and calls `chrome_message_for_event(payload)` instead of fabricating a new value — this exactly mirrors the pre-existing `OutputGap` arm's pattern at [`main.rs:564`](file:///home/tstapler/Programming/tymux/crates/tymux-cli/src/main.rs#L564) (`Some(ref payload @ attach_event::Payload::OutputGap(_)) if copy_mode.is_none() => { write!(stdout, "{}", chrome_message_for_event(payload).unwrap())?; ... }`), confirmed by direct read to already exist and already compile. `chrome_message_for_event` (confirmed at [`main.rs:815-821`](file:///home/tstapler/Programming/tymux/crates/tymux-cli/src/main.rs#L815-L821)) only pattern-matches the variant tag (`attach_event::Payload::Exited(_) => Some(...)`) and never reads the inner value, so passing the real `payload` through requires no `ExitStatus` construction at all — the plan's claim is accurate. The test site is fixed by building a real `ExitStatus { code: None }`/`Some(0)`, which will compile once the type also carries `ExitStatus` in scope.
