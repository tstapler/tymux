# Validation Plan: stapler-squad-integration

**Date**: 2026-08-21

## Happy Path Scenario
Given a stapler-squad session configured to use `BackendTymux` (per-session opt-in; `BackendTmux` remains the default, per requirements.md's Baseline), when a user starts a Claude Code agent through it, closes their laptop for an extended period, and reopens the dashboard tab, then Claude Code is still running (Epic 1.1's disconnect-survival fix), the terminal immediately shows its current on-screen state via the priming snapshot (Epic 1.3) instead of a blank screen, and once the agent later exits its exit status is queryable through `BackendTymux` (Epic 1.2/2.4) — with every `BackendTmux` session completely unaffected throughout (Success Metric 5).

Error paths and edge cases below are variations on this one flow: the daemon being unreachable instead of running, the stream dropping instead of staying open, the pane dying instead of surviving, the exit code being unknown instead of known. None of them is weighted equally with the core flow — each exists because a step in the happy path can fail, and Surface 3/4 of `design/ux.md` are literally "what UX-1's flow looks like when a specific link in this chain breaks."

## Test Stack
- **Unit (tymux, Rust)**: built-in `#[test]`/`#[tokio::test]` (existing convention in `crates/tymux-core/src/pane.rs` and `crates/tymuxd/src/main.rs`'s `#[cfg(test)] mod tests`), `insta` for golden-snapshot assertions (matching `crates/tymux-e2e`'s established pattern), `tracing-test` for log-level assertions (new dev-dependency, small and single-purpose — matching the project's build-vs-buy preference for hand-rolled/minimal deps over heavier alternatives)
- **Unit (stapler-squad, Go)**: standard `testing` package + `github.com/stretchr/testify` (`assert`/`require`, already the house convention per `tmux_backend_test.go`), hand-rolled fakes embedding the target interface for partial implementation (matching `mockTmuxManager`'s existing shape) rather than a mocking-framework dependency
- **Integration (tymux)**: `#[tokio::test]` against an in-process `TymuxDaemon` (existing `spawn_test_server` helper in `main.rs`) for anything not requiring a real OS-level pty/session; `crates/tymux-e2e`'s `CliHarness`/`daemon::spawn` for real-binary, real-pty tests including `disconnect_survival_e2e.rs`
